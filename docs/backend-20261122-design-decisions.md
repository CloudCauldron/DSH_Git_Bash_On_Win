# Backend design decisions — 22 November 2026

The plugin runs Git Bash under DSH 0.2.2-rc.5 on native Windows x64 from a shallow tree of ordinary executable copies, using a private MSYS runtime that loads an in-process compatibility DLL. Primary qualification ran on Windows 11 with both `ucrt64` and `mingw64` Git, and a separate Windows 10 host exercised a cross-volume deployment. The shipping revision before this change was `33fa0a9039d193452ccab7eefc222144437f8aaa`.

The [Windows experiments](analysis_report/refactor-design-validation/README.md) explain the loader, lifetime, and storage constraints behind the redesign, and the [November 17 design](backend-20261117-design-decisions.md) covers the superseded process-family backend.

## Execution and native admission

DSH owns confinement, grants, process creation, stdio, deadlines, and managed-range settlement. At the invocation-local spawn boundary, the plugin replaces the validated Bash command tail and finalizes `PATH`, `GIT_EXEC_PATH`, `GIT_TEMPLATE_DIR`, and `MSYS2_PATH_TYPE`, while preserving DSH's environment-map ordering and the runner's `TMP` and `TEMP`. The private `commandReceiver` in `src/index.ts` tracks command completion, and `src/adapter.ts` handles Loader and settings integration.

The executor holds the raw subprocess handle and runtime lease until `waitForExit()` confirms settlement, leaving the command owned if a wait fails. During disposal, it terminates any retained child even if `ShellExecution` already reports it killed, joins an active wait if one is running, and retries if an earlier wait failed. Repeated unconfirmed waits for the same command emit one diagnostic while keeping distinct wait errors visible. As observed with stock `pwsh-sandbox`, a native descendant of a packaged root can still outlive managed-range settlement. [Measured AppModel counterexample](analysis_report/refactor-design-validation/evidence/managed-range.md)

If a deadline or cancellation hits during workspace resolution or confinement, DSH returns immediately while in-flight preparation keeps its runtime reference until it settles, and disposal joins that work. The executor runs each release attempt once and preserves any failure for diagnosis.

A cold command checks for workspace overlap before creating the cache or writer lock; a ready command acquires its generation reference first. The plugin validates an absolute workspace path, resolves it once with `fs.realpath.native`, and passes an invocation-owned policy containing that canonical path to DSH before confinement applies grants. DSH independently runs `canonicalPath()`, and the plugin verifies that the returned path and policy mode match the admitted values.

The ACL runner enforces the workspace SID, while the plugin validates paired SID flags and the exact temp capability encoded in its view name. Agentless workspace-write uses the explicit `ww-u` view form because the runner creates its private temporary directory only after confinement returns, keeping grant lifetimes with DSH.

### Loader and token admission

The zero-CRT shim installs five MSYS import address table (IAT) hooks after verifying the exact loader path, mapped-file identity, policy, and token, then restores read-only memory protection. Any DLL matching the MSYS basename with a missing, malformed, oversized, or unexpected full path is rejected. Admission inspects `TEMP` first and falls back to `TMP`; because MSYS children can lack both variables during DLL initialization, their admission falls back to token and default-DACL evidence. Native and packaged children never receive the shim. [Loader and environment observations](analysis_report/refactor-design-validation/evidence/loader-and-shim.md)

The section ACL adjustment applies only to `cygpid.<pid>` inside the view's global MSYS object directory. Both qualified runtimes create named process sections there, use a separate directory for Windows-session objects, and abort if creating the global directory fails—so matching session directories would widen the grant to unrelated objects. Imported function names are matched with exact case, and unreadable ACEs are ignored. [MSYS 3.6.10 section creation](https://github.com/git-for-windows/msys2-runtime/blob/5a1665c8/winsup/cygwin/kernel32.cc#L280-L350) · [MSYS 3.6.9 directory selection](https://github.com/git-for-windows/msys2-runtime/blob/b4195d69/winsup/cygwin/mm/shared.cc#L29-L91)

Because a native caller can invoke Bash using NTFS 8.3 short names, the shim compares the loader's original sibling paths first and, if the admitted view contains a tilde, expands it with a bounded Windows long-name lookup before deriving the MSYS namespace and parsing the policy leaf. The on-disk and mapped MSYS identities must still match, and the expanded leaf must pass the same policy and token checks. This keeps the policy grammar and patch ABI unchanged, while the updated bundled DLL digest invalidates earlier copies.

The shim reads the logon SID through `TokenLogonSid`, which native tests cross-check against `TokenGroups` in all three modes. Admission verifies the entry count, returned size, SID bounds, required logon-ID attributes, and restricting-SID membership, copying the SID into bounded stack storage to avoid heap allocation or fallback paths under loader lock.

### Child executable selection

The `CreateProcessW` hook redirects direct launches of executables in the source or runtime `usr/bin` into the active view, using the mandatory `etc` junction to identify the source root while keeping the native `bin/bash.exe` wrapper distinct. Unrelated executables keep their original path, and a failed rewrite returns an error instead of falling back to the installed source. Overflow during input handling, long-name expansion, or output formatting returns `ERROR_FILENAME_EXCED_RANGE`.

Long-name lookup preserves any caller-supplied extended-length prefix, which root comparison then strips from the result, and root resolution propagates Win32 open and close errors. Outside DLL attach, `InitOnceExecuteOnce` publishes either the resolved roots or a terminal error and completes the callback in both cases, since returning `FALSE` would allow retries. [Microsoft once-initialization contract](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-initonceexecuteonce)

## Cache construction and lifetime

Each generation owns ordinary copies of Git's flat executable directory, so preparation needs only ordinary user permissions and works even when Git and the cache live on different NTFS volumes. Copying preserves each executable alias: on the measured `ucrt64` installation, 355 source files totaled 92,906,374 bytes, and adding the patched MSYS DLL and shim brought a generation to about 88.62 MiB. Other Git resources remain junction-backed, so all DSH instances sharing an installation must close during same-root Git upgrades while those source directories change. [Pinned-session replacement experiment](analysis_report/refactor-design-validation/evidence/storage.md)

Both selectable Bash entry points require ordinary source `etc` and `bin` directories plus the native `bin/bash.exe` wrapper, and the builder re-checks them before creating the private layout. Discovery, provisioning, warm admission, and tests share this contract: the `etc` junction identifies the source root for child redirection, `bin` exposes the native wrappers, Perl/library/libexec directories stay linked, and Git's temporary and device directories are omitted.

Junction admission reads the stored target, walks each directory component without following reparse points, and compares the target's NTFS volume and file ID against the admitted directory. That distinguishes ordinary directories whose names JavaScript lowercases identically and rejects any intermediate junction even if it currently resolves to the right tree.

Storage stays inside the owned DSH-home cache with its delete-on-close sibling writer lock. Both the owner marker and selector use `schemaVersion: 1`. Preparation and offline purge require the marker to name `dsh-git-bash-on-win/runtime-cache` and match the canonical root path, NTFS volume, and file ID; any missing marker or mismatch aborts before modifying the directory. Short generation and view paths along with a 260-byte UTF-8 guard reject over-budget homes before copying begins, and source/cache/workspace overlap is rejected before grants or writes.

### Copying the executable directory

The builder opens each source file without following reparse points using a short-lived `FILE_SHARE_READ` handle. That single handle supplies the file kind, identity, and `BigInt` size—bounded to 64 MiB for payload files and smaller limits for metadata—before allocating a buffer and reading once, while freshness sampling opens a separate handle. Reads fail on short data, growth past EOF, or size-conversion overflow.

A shared Node `wx` writer creates each independent file with inherited cache permissions, preserving any pre-existing file on collision and reporting write, close, and rollback failures together. Close errors on unpublished payloads abort the attempt, and native hold, lock, and claim close failures are fatal. [Read-only copy controls](analysis_report/refactor-design-validation/evidence/storage.md#how-to-copy-a-read-only-executable)

One source pin and one destination directory pin bracket the flat copy, while standalone metadata writes take their own pins around the same writer. Because MSYS is patched and written first, an unsupported image fails before any ordinary payload file is copied. The builder closes each file before yielding, checks cancellation between files, and closes its directory holds on exit. Path-based creation and publication fit the cooperating-host cache model; defending against deliberate parent-directory tampering by another process running as the same user would require a separate handle-relative destination writer.

### Freshness, admission and publication

The source freshness key combines the Git and MSYS file stamps with the raw SHA-256 of optional `etc/package-versions.txt` (bounded to 256 KiB, stored in the selector as `null` or 64 lowercase hex digits). A malformed selector in an owned cache triggers fresh preparation, and the builder re-checks the entire key before publication. This catches standard packaged upgrades without running Git or walking the whole tree, while **Save and rebuild** repairs custom edits that happen to preserve the key. Each `prepareRuntime()` call reads and hashes its own copy of the bundled shim, and ready commands reuse the admitted generation.

When the source key matches, warm admission checks both shells and both private DLLs before classifying the generation as stale, ensuring a missing shell or digest mismatch cannot mask an access, structural, or close error in another required file. Missing ordinary Bash/sh/DLL payloads or digest mismatches—including an updated bundled shim with an unchanged patch ABI—trigger a rebuild, whereas unexpected reparse points, redirected or dangling junctions, wrong file types, and access/read/close failures remain hard errors. A failed automatic rebuild never falls back to stale copies on disk. New files and junctions are validated as they are created and patched bytes are hashed before writing, avoiding a second full scan of the destination tree before publication.

To publish, the writer holds both the writer lock and a generation pin while DSH atomically replaces `current.json`; once that rename succeeds, the new selector stays committed even if cancellation or cleanup follows. Readers open a pin and then re-read the selector to rule out races, while collectors claim an unused generation exclusively before traversing it. Because the builder pre-creates the view directory (`v/`), command admission can reuse a view synchronously after checking its junction against the pinned runtime.

### Collection and disposal

Collection runs during builds and offline purge. Under the writer lock, a build scans unselected orphans once and, after publication, tries to collect only the generation it just superseded. Releasing a pin cleans up its owned views and closes the directory hold. Because active commands or peer processes may still pin the superseded generation—and there is no fixed generation quota or background collector—an immediate second pass would add work without ensuring reclamation; old copies remain until a later build or purge.

Active work and cleanup use separate promise sets so a rebuild can publish generation B while a command continues running on A, and new preparation drains cleanup without waiting for that command to finish. Disposal joins in-flight preparation and owned children, closes instance handles, and attempts best-effort view cleanup.

Offline purge verifies ownership, claims generations, and unlinks reparse points without following their targets. It deletes the ownership marker after payload removal, immediately before removing the empty root; if the process is killed between those two steps, the remaining empty markerless directory is refused by subsequent admission. Any blocked or interrupted purge reports failure.

## Build, packaging and dependencies

Runtime and build code share a bounded PE header, section, and import parser alongside the fixed MSYS patcher. The parser preserves ordinal imports and repeated descriptors and exposes DLL characteristics and export-directory fields, while build-only code inspects shim exports and enforces mitigations and allowed imports. The patcher keeps existing section positions and supported symbol/debug tails intact, checks new section-header space against both raw data and `SizeOfHeaders`, updates initialized-data size and checksum, and keeps the IAT span read-only. Source admission validates PE structure rather than a fixed source-hash whitelist; tested Git versions are recorded separately.

The patcher accepts only unbound MSYS imports. Both qualified Git images carry zero descriptor timestamps and forwarder chains, so rejecting bound descriptors preserves the original IAT bytes without adding rebinding logic. The reader also requires an eight-byte-aligned NT header after the DOS header, nonempty mapped sections, and nonempty names, keeping the checksum field aligned, giving every section a distinct address, and rejecting malformed imports before publication. [Microsoft PE format](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format)

The canonical native source lives outside the generated `lib/` directory. A single build script compiles it in a private temporary directory with the reviewed zero-CRT flags and `/Brepro`, verifies cleanup, and enforces PE invariants and the named-function allowlist on every build. Checking allowlist membership rather than exact import equality lets removed imports pass without a manifest edit while still requiring review for any newly added import. A DLL-only allowlist or API deny-list would miss unsafe functions, and a release hash alone cannot validate an unapproved development candidate.

Development builds report their actual tool versions and DLL hash so they can be tested before hash approval, whereas release builds and `prepack` require the recorded toolchain and approved hash. Before updating pins, two isolated builds are compared byte for byte, followed by qualification of the final DLL and tarball. Builds clean `lib/` first to drop stale outputs, package the compiled DLL without native sources or build scripts, and require no compiler at install time. Two-tree tarball comparison belongs in release qualification rather than recursive `prepack` runs; the build verifier reads DLL names directly from the manifest, and the isolated-build test injects invalid ambient compiler options and search paths to ensure builds do not depend on them.

The package declares five direct runtime dependencies: `@deepseek-ai/schemastery`, `@deepseek-ai/dsh-atomic-write`, `@deepseek-ai/dsh-error`, `@deepseek-ai/dsh-win32-process`, and `koffi`. Host Cordis and ACL peer identities stay shared, and SID-helper imports stay outside the standalone purge graph. `runtime-cache` resolves the bundled DLL at `../../lib/dsh-msys-compat.dll`, which works identically from source tests and packaged output. Obsolete filesystem exports were removed along with their debugger and setup callers. The workspace adds the UI-primitives development pin and release-age exclusion, pruning other exclusions only once the retained dependency graph no longer needs them.

## UI and verification boundaries

The settings page uses native `SettingsForm`, `SettingsValueField`, `Modal`, and `Toast` controls with page-local state and a single rebuild endpoint. It preserves Save and rebuild, revision-conflict handling, blank-path reset, unchanged-path rebuilding when settings are read-only, and the distinction between a saved path and a rebuild failure. Rich error details render inside `Modal` children. Async state updates are guarded against unmount and handle rejections; navigating away lets an accepted backend rebuild continue, and clicking again surfaces the existing busy response. The global overlay, feedback/progress transport, and custom styling were removed, while `src/locale/` stays unchanged.

### What the maintained tests cover

Cache and PE tests use a small, independently encoded PE32+ MSYS fixture containing the five required named imports, valid terminated descriptors and thunks, header room, and read-only IAT data, running it through the real patcher with no production exceptions. Malformed fixtures assert the exact diagnostic for each invariant, and the native invalid-UTF-16 test sets the lone surrogate directly via Win32 because Node replaces lone surrogates before the OS sees them. Full executable and native qualification still runs against owned real Git trees in both layouts; the synthetic fixture's size is just an implementation detail, not a 1.5 KiB target.

Tests share observers through `test/fixtures.ts`. Exhaustive PEB, token, and ACL negative controls plus 100-fork stress testing live in `native-compat.test.ts`, while real-executor tests cover argv, environment, policy, lifetime, representative image/view/fork checks, and four-caller IPC. Settlement tests count waits and recorded failures across both disposal orderings, and environment tests delete `PATH` at each caller layer while verifying that both runtime directories remain. Native Windows integration tests require installed DSH and assert the specific ownership, schema, or sharing error for each refused operation. Reused-view tests permit junction validation while forbidding selector, freshness, and DLL re-reads, and UI tests check native form usability and rich dialog content rather than custom geometry or paragraph tags.

Browser testing runs as part of `test:release`. Preflight checks DSH, Git, and Chrome before builds or fixture setup, resolving Chrome via `CHROME_PATH` or the Program Files default through a small shared helper; missing Chrome fails preflight instead of skipping the browser suite. UI-only test runs keep the DLL from an earlier full build and verify that it exists, leaving PE validation to build, native, and release checks, while native edits require a full build.

A shared preparation can outlive a timed-out caller, provided that timed-out command never spawns later. Optional alias and GDB checks live in explicit host qualification (`test/qualify-host.ts`), with WinGet logging opt-in and missing prerequisites reported as `UNVERIFIED`. Tests preserve normal endpoint protection without changing settings or recommending exclusions.

Both READMEs document practical differences from native Linux Bash, accepted command limits, retained-generation storage, all-instances-closed Git upgrades, and automatic next-use rebuilding. Manual rebuild is positioned as a repair tool, and complete removal clears only the plugin override, closes sharing hosts, purges once, and removes the package via DSH while preserving shared Shell settings.

## Release qualification

The release gate verifies the installed DSH version, Git layout, and Chrome executable before creating profiles or rebuilding, then runs type checking, lint, a clean pinned build, the Windows and browser suites, and two ordinary `pnpm pack` builds from separate source trees sharing the same build tools. Each tree starts with stale generated files and a different invalid DLL; the release test compares the resulting tarballs byte for byte and checks that the clean build matches the Git index for the shipped library.

Both test profiles use the rc.5 Web bundle template—the same template Electron uses to initialize Desktop—and install the tarball through DSH's package manager with scripts disabled and automatic peer installation off. Each profile runs its configured Shell and adapter entries through the DSH Loader in a separate Windows Node process, confirming that the packed preset inherits from the host's `AgentPreset` class and distinguishing all three policies with workspace and sibling write probes. Each process exits to release native modules before package removal, and standalone purge runs in a fresh process restricted to the installed profile's dependency graph, including a check that removing one profile leaves the published generation intact for the other.

The benchmark compares the installed copy package against the recorded shipping revision on disposable Git trees, timing a builtin, a pipeline, and Git through positive DSH managed-range settlement, with direct full-access Bash as a baseline. Warm admission measures the first preparation in a fresh Node process and confirms that the selector stays unchanged; fresh preparation, ready-use cost, and bytes retained across rebuilds are measured separately. See the [release audit](analysis_report/copy-backend-verification/evidence/release.md#independent-release-audit) for the qualified archive and the [timing report](analysis_report/copy-backend-performance/evidence/packed-runtime.md) for all distributions and rounds.
